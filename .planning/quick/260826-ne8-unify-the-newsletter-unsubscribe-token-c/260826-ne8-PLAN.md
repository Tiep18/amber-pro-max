# Quick Task 260826-ne8: Unify newsletter unsubscribe token contract

<objective>
Replace the split newsletter raw-token rules with one production contract matching the already-deployed transactional-email HMAC output, and prove the complete derivation, delivery, and redemption path.

Purpose: Newsletter emails currently derive a 43-character base64url HMAC token while redemption accepts only a legacy 64-character hexadecimal raw token. The correction must fail closed at every application boundary without retaining or leaking raw bearer material.

Output: One shared token contract, guarded worker/renderer/redemption paths, hash-only persistence, and an integration test that exercises the real production functions end to end.
</objective>

<interfaces>
Existing production seams the implementation must preserve:

- `deriveTransactionalEmailToken(secret, outboxId, purpose)` returns the domain-separated HMAC-SHA-256 base64url bearer value.
- `renderTransactionalEmail(row, context)` receives `context.newsletterToken?: string | null` and renders the localized unsubscribe URL for `newsletter_subscribed`.
- `unsubscribeNewsletter({rawToken}, client, recordOperationalFailure?)` maps public results to `unsubscribed | unavailable | invalid | error` and is the only page-facing redemption entry point.
- `TransactionalEmailRepository.issueNewsletterToken(row, preparation)` receives transient raw material but the Supabase repository inserts `token_hash`, expiry, normalized email, and source outbox ID only.
- `public.unsubscribe_newsletter(p_token_hash text)` validates a 64-character lowercase SHA-256 hex hash; this database contract is already correct and must not be migrated.
</interfaces>
