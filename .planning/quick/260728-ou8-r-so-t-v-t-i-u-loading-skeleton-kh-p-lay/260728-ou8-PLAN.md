## Scope boundaries

- Keep the seven existing `loading.tsx` files as thin delegates unless an export rename requires a wiring-only update.
- Change skeleton geometry to follow the resolved content; do not change real page layouts to make tests pass.
- Keep all skeletons as server-compatible presentation components using the existing `Skeleton` primitive. Add no dependency, timer, data fetch, client state, or authoritative commerce placeholder.
- Preserve public route `force-static`, `revalidate`, metadata, JSON-LD, auth, checkout, payment, and catalog projection behavior.
- Limit the skeleton to meaningful first-fold structure; do not duplicate the entire resolved page or create excessive off-screen placeholder DOM.

## Task 1: Replace generic route fallbacks with route-specific responsive geometry

**Files**

- `src/components/loading/page-skeletons.tsx`

**Action**

- Retain one `LoadingRegion` announcement and mark repeated decorative blocks `aria-hidden`; do not create nested live regions or focusable placeholder controls.
- Rebuild each exported skeleton from the canonical content classes listed in **Read first**:
  - `StorefrontPageSkeleton`: mirror the homepage first fold, including the `min-h-[620px]` mobile hero, the `lg:min-h-[540px]` two-column `0.86fr/1.14fr` split, responsive CTA rows, and the large-plus-two-small media collage rather than a generic product grid.
  - `CatalogPageSkeleton`: mirror the compact page header, product-type tabs, `260px` desktop filter rail, mobile filter/control row, result-count line, and product grid. Use one column below 480px, two from 480px, and three at `lg`.
  - `ProductPageSkeleton`: mirror the square bordered gallery, optional thumbnail rhythm, breadcrumb/title/wishlist row, commerce block height, purchase-info rows, and the exact `lg` gallery/detail split.
  - `CheckoutPageSkeleton`: mirror the back-link/title/intro header, one continuous contact/destination card, `400px` sticky summary column, mobile bottom padding, and an `lg:hidden` fixed mobile checkout dock placeholder.
  - `AccountPageSkeleton`: assume `AccountShell` is already mounted; mirror the overview header with its desktop identity panel and render four border-separated destination rows instead of three standalone cards.
  - `OrderPageSkeleton`: mirror the `1fr/380px` payment-and-summary layout, with stacked left status/fulfillment panels and a sticky right summary rather than a three-card dashboard.
  - `AdminPageSkeleton`: mirror `AdminPageShell`/`AdminPageHeader`, the `md:grid-cols-3` attention/pulse region, and the `md:grid-cols-4` metric grid; do not render the current unrelated four-stat-plus-table shape.
- Extract small neutral primitives only where they prevent drift (page heading lines, summary rows, product card), but allow route-specific composition and breakpoint classes instead of forcing every route through one generic skeleton.

**Verify**

- Automated: `npm run typecheck`
- Browser: at 390x844 and 1440x900, force a slow client navigation to each existing loading boundary and capture the loading and settled states. Confirm matching container edges, first-fold vertical start, column mode, media ratio, mobile-only/desktop-only regions, and no horizontal overflow.

**Done**

- All seven route fallbacks visually preserve the major mobile and desktop geometry of their resolved content, while remaining neutral, non-interactive, and free of commerce facts.

## Task 2: Unify catalog pending cards and lock responsive alignment with tests

**Files**

- `src/components/loading/page-skeletons.tsx`
- `src/components/catalog/catalog-commerce.tsx`
- `tests/unit/ui/loading-boundaries.test.ts`

**Action**

- Export a reusable neutral product-card skeleton whose outer shell follows `ProductCardView`: rounded/ringed card, `aspect-[5/4]` media, `grid-rows-[auto_1fr]`, and responsive `p-3 sm:p-5` body rhythm. Use it in both `CatalogPageSkeleton` and `CatalogProductGridSkeleton`; preserve the latter's 12-item count, `data-testid`, request-state behavior, and `CatalogCommerce` state machine.
- Extend `loading-boundaries.test.ts` with a route-to-content contract table. For each skeleton, assert the canonical mobile and desktop class fragments also used by its resolved page/layout: homepage hero split/min-heights, catalog filter/grid breakpoints and `5/4` card ratio, product split/square gallery, checkout `400px` summary plus mobile dock visibility, account overview split/four rows, order `380px` aside, and admin `md` dashboard grids.
- Keep the existing delegation, accessible busy-state, no-authority-import, and public static/ISR assertions. Add guards that decorative skeleton blocks are not links/buttons and that no price, stock, payment, order-number, signed-URL, or entitlement value is rendered.
- After automated checks, repeat the 390px and 1440px loading-versus-settled comparison. Treat a mismatched column count, container edge, primary media ratio, fixed mobile dock, or visible layout jump as a failure; correct the skeleton, not the content.

**Verify**

- Automated: `npm run test:unit -- tests/unit/ui/loading-boundaries.test.ts`
- Automated: `npm run lint`

**Done**

- Route and in-page catalog loading states share the same responsive product-card geometry, and focused tests fail when a skeleton drifts from the content layout or gains authoritative/interactive behavior.
