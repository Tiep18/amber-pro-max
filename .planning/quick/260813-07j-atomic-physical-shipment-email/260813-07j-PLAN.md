# Atomic Physical Shipment Email Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make physical fulfillment state, event history, and shipped-email intent commit or roll back together.

**Architecture:** A narrow authenticated Supabase RPC becomes the sole persistence boundary. PostgreSQL locks and validates the fulfillment row, derives order/email facts, and performs all writes in one transaction; the Next.js module becomes a strict intent/result adapter.

**Tech Stack:** PostgreSQL 17/PLpgSQL, Supabase RLS/Auth/PostgREST RPC, Next.js 16 server actions, TypeScript 5.9, Zod, Vitest, pgTAP.

## Global Constraints

- Follow the approved design at `docs/superpowers/specs/2026-08-12-atomic-physical-fulfillment-email-design.md`.
- Do not add a queue, worker, cron, package, database service, or paid Vercel/Supabase feature.
- Do not accept recipient email, locale, order number, actor ID, timestamps, or rendered email payload in the RPC input.
- Do not expose raw database/provider errors, customer PII, tracking values, or admin notes through operational failure facts.
- Preserve existing physical transition semantics, including same-state updates and shipped-without-tracking support.
- Persist the existing admin note field privately; authenticated customer reads must not gain access to it.
- Do not alter payment confirmation, entitlement granting, email rendering, Resend retry behavior, guest claims, or manual download resend.

## Threat Model

| Threat | Boundary | Mitigation |
| --- | --- | --- |
| Shipped state commits without email intent | admin action -> Postgres | One RPC transaction rolls back update/event/outbox together. |
| Browser substitutes recipient or locale | form -> RPC | RPC payload excludes those fields and loads them from `checkout_orders`. |
| Concurrent admin overwrites newer state | admin action -> fulfillment row | `FOR UPDATE` plus exact expected status/version check. |
| Non-admin invokes privileged mutation | authenticated API -> function | `private.is_admin()` inside security-definer function and authenticated-only execute grant. |
| Sensitive failure evidence leaks | database/application -> operations | Bounded result/error mapping and safe fact whitelist. |
